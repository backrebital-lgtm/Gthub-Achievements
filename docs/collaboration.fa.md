# روال همکاری

## صف کار

Issue باید مسئله و معیار پایان داشته باشد. نگهدارنده پس از بررسی، برچسب `ready-for-work` را اضافه می‌کند. هماهنگ‌کننده در اجرای بعد، کار بدون مسئول را به حسابی که کار باز کمتری دارد واگذار می‌کند. هر حساب حداکثر دو Issue بازِ واگذارشده دارد. کار دارای برچسب `blocked` یا مسئول قبلی دست‌نخورده می‌ماند.

برای کارهای آمادهٔ بدون مسئول، وابستگی بومی GitHub (`blocked by`) هم خوانده می‌شود. اگر مانع هنوز باز باشد واگذاری انجام نمی‌شود؛ مانع بسته‌شده مانع واگذاری نیست. برچسب `blocked` توقف دستی قطعی باقی می‌ماند و برای کارهایی که وابستگی بومی ندارند باید استفاده شود. اگر فهرست وابستگی HTTP ۴۰۴ یا ۴۱۰ بدهد، این اجرا وابستگی را خالی فرض می‌کند و فقط برچسب را ملاک می‌گیرد. هماهنگ‌کننده وابستگی ایجاد یا حذف نمی‌کند و عنوان/بدنهٔ Issue مانع را در گزارش کپی نمی‌کند.

برچسب `priority:high` جلوتر از `priority:normal` پردازش می‌شود. برچسب‌های `area:docs`، `area:automation` و `area:tests` موضوع کار را مشخص می‌کنند.

## بررسی PR

PR غیرپیش‌نویس یکی از دو عضو برای عضو دیگر درخواست بررسی می‌گیرد. درخواست موجود تکرار نمی‌شود. تأیید commit قبلی برای commit تازه کافی نیست. درخواست اصلاح با ثبت commit جدید خودبه‌خود حل‌شده محسوب نمی‌شود و در گزارش باقی می‌ماند؛ پس از تغییر commit، بررسی مجدد درخواست می‌شود. review تازه یا کنارگذاشتن رسمی آن تعیین‌کننده است.

گزارش وضعیت یکی از `needs-review`، `review-requested`، `changes-requested` یا `approved-current-commit` را نشان می‌دهد. این صرفاً وضعیت review است؛ به معنی اجازهٔ merge یا موفقیت تست‌ها نیست. PRها به ترتیب شماره بررسی می‌شوند. برای بیش از سقف `maxPullsPerRun` (پیش‌فرض ۲۰)، فقط همان تعداد به‌تفصیل خوانده می‌شود؛ بقیه در گزارش با «نیازمند بررسی» و یک خط توجه باقی می‌مانند. فهرست ناقص API به‌عنوان موفقیت منتشر نمی‌شود.

گردش‌کار هر بار حداکثر شش واگذاری یا درخواست بررسی انجام می‌دهد و یک Issue گزارش را در صورت تغییر به‌روز می‌کند. هیچ PR را با این اسکریپت merge یا approve نمی‌کند. نوشتن محتوا و بررسی کد را وظیفهٔ ساعتی Codex انجام می‌دهد؛ تمام پیام‌های عامل باید خودکاربودن را اعلام کنند. سقف `maxPullsPerRun` هم برای بررسی تفصیلی PR و هم برای خواندن `blocked by` کارهای آماده به کار می‌رود؛ موارد باقی‌مانده واگذار نمی‌شوند و در گزارش ذکر می‌شوند.

## معیار ادغام توسط Codex

1. مسئلهٔ مشخص و تغییر مرتبط وجود دارد.
2. تست متناسب با تغییر و CI برای آخرین commit موفق است.
3. diff واقعی بررسی شده و ایراد حل‌نشده ندارد.
4. PR و commit از زمان بررسی تغییر نکرده‌اند.
5. قوانین شاخه رعایت شده‌اند؛ تغییر مجوز و secrets نیازمند بررسی جداگانه است.

کار تمام‌شده با لینک PR در Issue مستند شود؛ پرسش‌ها برای ابهام واقعی همان کار مطرح شوند. فعالیت برای خالی نبودن گزارش یا افزایش شمارنده تولید نشود.

## اجرا و خطا

در `Actions → Hourly maintenance → Run workflow`، گزینهٔ `dry_run` به‌صورت پیش‌فرض روشن است و هیچ واگذاری، درخواست یا Issue جدید نمی‌نویسد. اجرای زمان‌بندی‌شده و رویدادهای Issue و PR اعمال تغییرات را فعال می‌کنند. نتیجهٔ هر اجرا تعداد صفحات خوانده‌شده، سقف بررسی PR، تعداد عملیات انجام‌شده و کارهای ردشده به علت تغییر همزمان را در Summary نشان می‌دهد. تست‌ها پیش از اولین درخواست نوشتن به API اجرا می‌شوند.

هماهنگ‌کننده برای رویدادهای PR از `pull_request_target` استفاده می‌کند و **فقط کد شاخهٔ پیش‌فرض همین مخزن** را دریافت و اجرا می‌کند؛ کد شاخهٔ PR، artifact یا دادهٔ قابل‌اجرای کاربران را اجرا نمی‌کند. token فقط در گام هماهنگی قرار دارد و مجوزهای آن محدود به خواندن محتوا و مدیریت Issue/درخواست review است. قوانین GitHub مجوزهای issues و pull-requests را در سطح API دسته‌بندی می‌کند؛ کلاینت همین پروژه فقط واگذاری Issue، درخواست بررسی، و ایجاد/به‌روزرسانی Issue هماهنگی را می‌نویسد.

خطای شبکه یا خواندن موقت API حداکثر دو بار تکرار می‌شود. `Retry-After` رعایت می‌شود؛ انتظار بیشتر از ۳۰ ثانیه یا rate limit بدون زمان مشخص، اجرا را متوقف می‌کند تا اجرای بعدی بررسی کند. درخواست نوشتن تکرار نمی‌شود، زیرا ممکن است پاسخ گم شده باشد ولی تغییر ثبت شده باشد. نبود دسترسی، rate limit باقی‌مانده و خطای صفحه‌بندی اجرا را ناموفق می‌کند تا گزارش ناقص به‌عنوان موفق منتشر نشود. درخواست اصلاح و تأیید همزمان، تغییر head، واگذاری دستی و ظرفیت کار پیش از نوشتن دوباره خوانده می‌شوند؛ API چند درخواست اتمیک نیست و تغییر دقیقاً همزمان همچنان نیازمند بررسی اجرای بعدی است.

### عیب‌یابی

- **زمان‌بندی دیر شده:** در Actions زمان و نوع آخرین اجرا را ببینید. طبق مستندات GitHub، schedule تضمین اجرای دقیق ندارد؛ رویدادهای Issue/PR وابستگی به آن را کم می‌کنند. در صورت نیاز ابتدا dry-run و سپس یک اجرای دستی انجام دهید؛ اجرای درحال‌انجام را تکرار نکنید.
- **اجرا سبز است ولی توسعه‌ای دیده نمی‌شود:** Actions فقط هماهنگ‌کننده است. صف `ready-for-work`، PRهای باز و وضعیت وظیفهٔ محلی Codex، روشن‌بودن سیستم و سهمیهٔ آن را بررسی کنید.
- **HTTP 401/403:** دسترسی workflow و عضو مخزن را بررسی کنید؛ token را در log قرار ندهید و مجوزهای گسترده یا PAT تازه نسازید. خطای 403 الزاماً rate limit نیست.
- **خطای شبکه/429/5xx:** اجرای ناموفق و وضعیت فعلی Issue/PR را بررسی کنید. نوشتن قبلی ممکن است موفق شده باشد؛ ابتدا وضعیت را بخوانید و فقط در نبود اجرای فعال مجدداً اجرا کنید.
- **CI ناموفق یا درخواست اصلاح:** merge نکنید؛ ابتدا همان PR را اصلاح و آخرین commit را دوباره آزمایش و بررسی کنید.

## گردش‌کارهای نقش‌محور

درخواست بررسی هنگام باز شدن PR و اعتبارسنجی `Co-authored-by` جدا از این هماهنگ‌کننده اجرا می‌شوند. هماهنگ‌کننده همچنان درخواست جاافتاده را جبران می‌کند و سقف `maxMutationsPerRun` دارد. شمارش PRهای ادغام‌شده فقط در `Collaboration progress report` و بدون ساخت Issue/PR است. شرح روزبه‌روز: [workflows.fa.md](workflows.fa.md).
